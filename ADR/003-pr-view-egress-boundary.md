# ADR-003: PR/MR 只读视图 —— 出网与凭据的边界

- **状态**：提案（**第四节「必须满足的边界」是本次的结论；是否实现 TASK-020 待批准**）
- **日期**：2026-10-10
- **决策者**：项目主导
- **关联**：`SPEC.md` US-10 与非功能需求「出网」、`SECURITY.md` 威胁 7、P-07 / P-08、
  `scripts/read-only-guard.sh`

## 摘要

US-10（PR/MR 只读视图）是 `SPEC.md` 里最后一张 P2 卡，做完之后 US-1~US-10 全部
`[已实现]`。但它会带来本项目**第一次非回环出网**，并且需要凭据 ——
这两件事都直接改写非功能需求里的那一行：

> 出网｜唯一出网点是回环地址上的本地模型服务，默认关闭

本 ADR **不实现**它，也不擅自把它删掉。它做的是三件事：

1. 把两条实现路径各自的**验证缺口**量出来（其中一条在本机一次都跑不了）；
2. 实测现有的只读扫描器面对「第二个二进制」时还剩多少防护（结论：基本没了）；
3. 定下**无论走哪条路都必须满足的边界**，以及「什么条件下才该动手」。

要不要做，以及做哪条路，留给人定。

## 一、问题

归档 `001.md` 第 194–195 行（本项目的权威需求来源）原文：

> ### US-10：PR/MR 只读视图（P2）
> 通过 `gh` CLI 或 API 只读展示 PR 状态、评审、CI 结果。

`SPEC.md` 至今仍是 `[待实现]`，`ROADMAP.md` 把它记为 TASK-020。

它与此前所有卡有一个**性质上的差别**：US-1~US-9 读的全是本地磁盘上的东西，
而 US-10 要读的数据在别人机器上。项目的只读宪法（`AGENTS.md`）与只读扫描器
都是围绕「Git 动词」建立的，对这条边界**没有任何覆盖**。

## 二、实测

### 2.1 本机没有 `gh`

```
$ which gh        → gh not found
$ ls ~/.config/gh → 不存在
```

这意味着 **`gh` 那条路在这里一次都跑不了** ——
和 TASK-013/014 的 Ollama 是同一类缺口：代码可以写，但「真跑一遍」不可能，
能逼近的只有自造 stub。而 P-08 已经确立过一条判据：

> 测试输入的来源决定它的证明力。自编 stub 的响应证明「代码自洽」，
> 证明不了「与外界的字段名一致」。

### 2.2 只读扫描器面对 `gh` 只剩一层，且恰好漏掉绝大多数写操作

扫描器的第 0 层门槛是「语句里出现 `Command::new("git")` 或 `self.run(`」，
只有过了这道门槛才走动词白名单（1）、危险选项（2）、条件动词（3）。
第 4 层（写动词黑名单）是全局的。

于是用 `Command::new("gh")` 另起一个二进制时，前三层**全部空转**。实测：

| 写法 | 扫描结果 |
|------|---------|
| `gh pr view` / `gh pr checks` / `gh pr diff` | 放行（本来就是只读，放行是对的） |
| `gh pr merge` | **拦住** —— 因为 `merge` 恰好也在 Git 的写动词表里 |
| `gh pr comment` | 放行 ❌ |
| `gh pr review --approve` | 放行 ❌ |
| `gh pr close` | 放行 ❌ |
| `gh pr edit --title` | 放行 ❌ |
| `gh release create` | 放行 ❌ |
| `gh repo delete` | 放行 ❌ |

**7 个写子命令里只拦住 1 个**，而且拦住它是**巧合**（`merge` 在 Git 里也是写动词），
不是因为扫描器认识 `gh`。

反过来，若复用 core 的 `self.run()` 去跑 `gh`，则每条都会报
「`pr` / `view` / `checks` 白名单外的子命令」——**过严**：只读的也被拦，
逼人去给白名单加词，而加词这一步本身就是风险。

> 两种写法都不是「刚好」。这条与 `ADR/002` 里那条「换 gix 会让扫描器空转」
> 是同一类问题：**安全门禁的有效性依赖于被扫代码的形状**，
> 形状一变，门禁可能安静地失效。

复现（扫描器接受目录参数，不必改动仓库内的文件）：

```bash
mkdir -p /tmp/ghprobe && printf '%s\n' \
  'fn a() { let _ = Command::new("gh").args(["pr", "comment", "1"]).output(); }' \
  'fn b() { let _ = Command::new("gh").args(["pr", "merge", "1"]).output(); }' \
  > /tmp/ghprobe/probe.rs
bash scripts/read-only-guard.sh /tmp/ghprobe   # 只报 merge 一条
```

### 2.3 出网边界目前是「测试兜底」，不是「扫描兜底」

`SECURITY.md` 威胁 7 已经写明：只读扫描器是 Git 动词白名单，**看不见 HTTP 调用**，
那条约束只由 `summarizer` 的四组测试兜底。若走直连 API 路线，
US-10 会落在**同一个盲区**里 —— 好处是那四组测试提供了可直接照搬的样板，
坏处是盲区会从「一处」变成「两处」。

## 三、两条路径

| | **`gh` CLI 子进程** | **直连 REST API** |
|---|---|---|
| 凭据 | 交给 `gh` 自己的钥匙串，项目不碰 token | 必须自己拿：要么存、要么每次传入 |
| 本机可验证性 | **零**（没装 `gh`） | 可用回环 stub 跑通（P-07 的基础设施现成） |
| 与外界的字段契约 | 随 `gh` 版本变，无法用官方文档钉死 | 可用官方 API 文档逐字取样（P-08 的做法） |
| GitHub Enterprise / 自建 | `gh` 自己认配置，天然支持 | 要自己解析 remote URL 并允许主机白名单 |
| 只读门禁 | 需给扫描器加一套 `gh` 子命令白名单（见 2.2） | 不适用（扫不到 HTTP），改由测试兜底 |
| 覆盖面 | GitHub（GitLab / Gitee 要 `glab` 之类，又是一个二进制） | 同样只覆盖 GitHub，除非抽象出 provider 层 |
| 新增依赖 | 无 | 需要 TLS（`ureq` 目前**刻意关闭**默认特性、依赖树里没有 `rustls`/`ring`） |

第三条值得单独说：P-08 之所以把「不遵循环境代理」写成**代码里的显式 agent**
而不是「依赖库的默认值」，就是因为默认值会变。US-10 若走 API 路线，
会第一次把 TLS 引入依赖树 —— 那是一个**不可逆的方向性决定**
（`SECURITY.md` 威胁 7 第 2 层明确记着「依赖树里没有 rustls」是一条防线）。

## 四、无论走哪条路都必须满足的边界（本 ADR 的结论）

1. **默认关闭，显式开启**。不开就不构造客户端、不读任何凭据、不发任何请求。
2. **主机白名单，而不是任意 URL**。判据必须是**解析出 host 后精确比对**，
   不得比前缀（威胁 7 第 1 层的 8 条输入原样适用）。
3. **凭据不落盘、不进日志、不进产物**。若走 API 路线，token 只存在内存里，
   由调用方每次传入；若将来要持久化，须另开一张卡并写明存放位置与加密方式。
4. **送出去的内容最小化**。参照威胁 7 第 3 层：可以送「PR 号 / 仓库 owner+name」，
   **不得**送仓库绝对路径、diff 正文与文件内容。这条必须有一组测试
   像 `tests/summarizer_http.rs` 那样**读请求体**来断言，而不是靠代码审查。
5. **只允许 GET**。若走 `gh` 路线，扫描器必须新增一套 `gh` 子命令白名单，
   并且**先证明它会红**（用 2.2 那 7 个写子命令当反例）——不会失败的门禁比没有门禁更危险。
6. **失败降级为「不可用」，不阻塞其它功能**。PR 视图拿不到，
   本地快照照常显示。
7. **非回环出网必须写进 `SPEC.md` 与 `SECURITY.md`**，
   「唯一出网点是回环地址」那一行要改写成「回环（本地模型）+ 显式授权的
   远端只读 API（PR 视图）」，并各自标明默认状态。

## 五、待批准的选项

| 选项 | 内容 | 代价 |
|------|------|------|
| **A（本 ADR 的建议）** | 暂不实现。US-10 保持 `[待实现]`，在 `SPEC.md` / `ROADMAP.md` 里指向本 ADR，写明「验证缺口 + 门禁缺口」两条理由 | US-1~US-10 不全绿 |
| **B** | 走 `gh` CLI。先给扫描器加 `gh` 白名单并证明它会红，再实现 | 本机一次都跑不了；只覆盖装了 `gh` 的机器；扫描器多一套规则要长期维护 |
| **C** | 走直连 API。用回环 stub + 官方文档字段契约把能验的验掉 | 引入 TLS（依赖树不可逆变化）；要定 token 从哪来；真实调用仍无法端到端验证 |

若选 B 或 C，还须同时决定：**是否覆盖 GitHub 之外的平台**。
归档原文只说「PR/MR」，`MR` 一般指 GitLab —— 全覆盖意味着 provider 抽象层，
工作量与上面任何一项同量级，建议**先只做 GitHub**并把范围写进 SPEC。

## 六、什么条件下重估

- 有了一台装了 `gh` 并已登录的机器（闭合 B 的验证缺口）；
- 或：明确接受「真实调用无法端到端验证」，且选定了 token 的取得方式（闭合 C 的缺口）；
- 且：第四节第 5 条那套门禁**已经写完并被证明会失败**（B）或第 4 条那组
  读请求体的测试**已经写完**（C）；
- 且：`SPEC.md` / `SECURITY.md` 的出网条款已按第 7 条改写。

四条不齐就动手，等于把一个「看起来做完了、其实没人验过」的功能
加进一个以「只读 + 本地优先」为卖点的工具。
