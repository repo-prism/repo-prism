# TASK-019: 多仓库工作区（US-9）

**状态**：已完成（2026-10-10）
**血统**：归档 `001` §US-9「多仓库工作区」，优先级 **P2**。
v0.3.0 发完（P0 全部落地）之后的第一张产品卡。

## 目标

同时打开多个仓库，在统一界面里切换。

## 上下文

- 此前 `AppState` 里只有一个 `Option<RepoSession>`，打开第二个仓库会**整体替换**第一个。
  这是 TASK-018 留下的明确边界（「多仓库工作区是 TASK-019 的范围，这里一次只留一个会话」）。
- `Git` 的方法全是 `&self`（内部用 `Mutex` + `AtomicUsize`），因此它是 `Send + Sync`
  —— 可以放进表里返回 `Arc<Git>`，在**表锁之外**执行命令。这是本卡的形状能成立的前提。
- 引用缓存的失效判据（TASK-018 的指纹）与「有几个仓库」无关，**可原样复用**。

## 关键决策

### 1. 键是「已解析的仓库根」，不是用户输入的字符串

2026-10-10 实测：同一个仓库的四种写法全部解析成**同一个绝对路径**：

| 写法 | `rev-parse --show-toplevel` |
|------|------------------------------|
| 仓库根 | `/private/tmp/probe019/repo` |
| 子目录（两级） | 同上 |
| 符号链接 | 同上（git 会解析链接） |
| 符号链接下的子目录 | 同上 |

所以拿解析后的根当键才是稳定的。用户输入的字符串只作为**别名**记下。

### 2. 同一仓库的新写法只补一条别名，不新建会话

否则「先用符号链接打开、再用真实路径打开」会建出两个会话，
各自缓存一份引用映射 —— 同一份数据读两遍，而且两个实例的 spawn 计数互不相干。

### 3. 命令在表锁之外执行

表只负责交出 `Arc<Git>`。两个不同仓库的命令因此**不互相阻塞**；
同一个仓库的两个命令也不阻塞（缓存自己有锁）。
这比 TASK-018 的「一把锁串起所有命令」松，但代价是**没有变差的项**：
引用缓存仍是每仓库一份。

### 4. 有上限，LRU 淘汰（默认 8）

无上限的表在长驻进程里会随「访问过的仓库数」无限增长内存。
每个会话最坏持有一份引用映射（TASK-018 的预算是 4 MiB）。

**淘汰只丢缓存，不丢正确性** —— 被淘汰后再打开只是重新读一遍引用，
结果与「从未缓存过」一致。退化的方向是「多起一个子进程」，不是「用过期数据」，
与缓存的既有取向一致。

### 5. 关闭连别名一起清

否则关掉之后立刻用原写法打开，会拿回刚关掉的那个会话（连同它那份还没失效的缓存）。
「关闭」的语义必须是**真的放掉**，不只是从列表里隐藏。

### 6. 不持久化打开的仓库列表

恢复上次打开的仓库需要把用户访问过的路径写进配置文件。
本项目的默认取向是「本地优先、不记录不必要的信息」，故不做。
重开应用只有一个空列表。

### 7. MCP 长驻进程复用同一张表

此前 MCP 每个请求都 `Git::open`（每次一次 `rev-parse`）。
MCP 是被客户端拉起后长期驻留的进程，复用是自然的收益。
失效判据与桌面端同一套（引用指纹），**不需要调用方声明「仓库变了」**。

### 8. 前端：切回已打开的仓库**不重新读取**

已打开仓库的快照 / 提交 / 分析 / 远端留在内存里，切换即渲染。
这与会话表是同一条原则的两次应用：**能不复用的才去起进程**。
另提供显式刷新（重新打开同一路径）。

## 验收标准

- [x] 四种写法（根 / 子目录 / 符号链接 / 符号链接下的子目录）命中**同一个**会话
- [x] 命中与否用 **spawn 次数 + `Arc::ptr_eq`** 证明，不是看返回值相等
- [x] 两个不同仓库互不干扰：各自的首次快照都是 2 次子进程，结果各自正确
- [x] 超过上限时淘汰**最久未用**的那一个
- [x] 被淘汰的仓库再打开仍能拿到正确结果（淘汰只丢缓存）
- [x] `close` 之后该仓库再打开会重新起进程（证明会话真的放掉了）
- [x] `close` 连别名一起清：关闭后用**另一种写法**打开，spawn 数必须回到 1
- [x] `roots()` 返回的是**已解析的仓库根**且**顺序确定**（`HashMap` 的顺序不确定，必须排序）
- [x] 非仓库路径返回 `Err`，且不占槽位、**不留别名**
- [x] `cap` 为 1 时退化为「一次只留一个」（与 TASK-018 行为一致）
- [x] 前端：切换已打开的仓库不重新读取；关闭后从列表消失
- [x] MCP：一个长驻进程能服务两个仓库；复用的会话**看得见**两次调用之间新建的分支

## 补的一张闸门：`scripts/check-invoke-names.mjs`

本卡新加了两个命令（`list_open_repos` / `close_repo`），而**命令名是字符串**：
两端没有编译期联系，只改一边的话 fmt / clippy / 测试 / build 全绿，
只有用户点了那个按钮才在运行时炸 —— UI 接线层正好是全项目唯一没有自动化
测试的地方。

于是把「前端 `invoke("x")` 的名字必须能在后端 `generate_handler!` 里找到」
变成一条会失败的断言，挂在 `pnpm check:commands`，并加进 `ci.yml` 的 frontend job。
**失败路径已实测**：把前端的 `list_open_repos` 改成 `list_opened_repos`，脚本 rc=1 并指出名字。

它**抓不到**参数名与参数类型（`{ filePath }` ↔ `file_path` 这类），
那要真跑才看得出来；脚本只守「名字存在」这一层，注释里写明了边界。

## 探针与实测

### 假设探针（写实现之前跑）

| 假设 | 实测 |
|------|------|
| 四种写法解析到同一个绝对路径 | ✅ 根 / 两级子目录 / 符号链接 / 符号链接下的子目录 → 全部 `/private/tmp/probe019/repo` |
| `Git` 是 `Send + Sync`（能进表并返回 `Arc<Git>`） | ✅ 方法全是 `&self`，内部 `Mutex` + `AtomicUsize` |
| 非仓库路径 | ✅ `rev-parse` 退出码 128 |

### 失败路径探针（写完测试之后跑）

| R2 | 同一仓库的新写法也新建会话 | `a_subdirectory_spelling_lands_on_the_same_session` |
| R3 | 关闭不清别名 | `closing_clears_every_alias_to_that_repo` |

| R10 | 关闭没有真的放掉会话 | `closing_releases_the_session` |

前端侧 7 条（`src/lib/repo.ts`）：结尾分隔符 / Windows 反斜杠 / 关掉之后选谁
（第一个 / 最后一个 / 唯一一个 / 不在列表里）/ 全是分隔符的输入。

**16 条全部变红。** 其中 R1 值得一提：它第一次用的变异是「加一行空语句」，
根本没碰到被测逻辑，于是报绿 —— 是**探针本身**的 bug，修正变异后才抓住。
（教训与 P-09 一致：反证脚本自身也会失效，且失效方向永远是「报告全绿」。）

### 一条被实测纠正的断言

`opening_a_second_repo_does_not_change_the_first_ones_cost` 原本断言
「A 的第二次快照仍是 2 次」，实测是 **1** —— 因为会话是 `open_cached` 的，
第二次读引用命中了缓存。这不是退化，是 TASK-018 的预期行为。
「`snapshot()` 恰好 2 次」那条**与状态无关**的契约由 `perf.rs` 用**不缓存**的
`Git::open` 钉住，两者不是同一条断言。已改成：
「A、B 的首次快照各 2 次，且读过 B 之后 A 的第二次仍是 1 次」
—— 后者才是本卡真正要证明的「缓存是每个仓库一份，互不顶掉」。
